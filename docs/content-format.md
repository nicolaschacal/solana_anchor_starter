# Evolution content schema 1

Root: `{schema:1, family:{id,name}, version, development, evolutions:[...]}`. `development:true` marks sample/balancing content. IDs and initialWeight are u16 (ID zero is unused), stage is 0..5, family 0..7, version 1..4294967294. Names: 48 UTF-8 bytes; modelUri: 512 bytes; 1..1000 evolutions, 16 paths per entry, 32 requirements per path. Empty model URIs and terminal forms are allowed with UI warnings. Unknown fields are rejected.

Stages: 0 Baby, 1 Byte, 2 Mega, 3 Giga, 4 Tera, 5 Peta. Families: 0 Mammal, 1 Aquatic, 2 Avian, 3 Reptile, 4 Insect, 5 Plant, 6 Humanoid, 7 Mythic.

Requirements: `{group:u8, metric:u8, operator:u8, value:u16}`. Metric numbers are scoped to their group. The array position below is the numeric metric ID, starting at zero. These numeric assignments are permanent for schema 1.

| Group | Metrics in ID order |
|---|---|
| 0 Genetics | ActivityGene, SociabilityGene, IndependenceGene, NocturnalGene, CarnivoreGene, HerbivoreGene, PiscivoreGene, FrugivoreGene, SizeGene, StrengthGene, SpeedGene, ResilienceGene, MutationGene, RarityGene |
| 1 Diet | Meat, Fish, Plant, Fruit |
| 2 Time | Morning, Day, Evening, Night |
| 3 Activity | Play |
| 4 Physical | Weight, Age |
| 5 Progression | Cycle, Level, XP |
| 6 Battle | Wins, Losses, HP, Attack, Defense, Speed |

Operators: 0 Eq, 1 NotEq, 2 Greater, 3 GreaterOrEqual, 4 Less, 5 LessOrEqual. Paths: `{target, requiredGroupCount, priority, requirements}`. Future semantics: AND requirements within each present group; count passing groups; qualify when count >= requiredGroupCount. Absent groups do not count. Count must be <= number of distinct present groups. Zero permits an unconditional path. No evaluator exists in this phase. Higher/lower priority gameplay selection is deliberately not implemented.

## Deterministic bytes

Validate schema first. All numeric values are nonnegative integers, safe in JavaScript. Strings must be valid Unicode with no control characters; this prototype restricts content text to non-surrogate BMP code points. No whitespace trimming, Unicode normalization or case folding is performed. Distinct strings remain distinct. Object keys are sorted lexicographically (all schema keys are ASCII). Encode strings with standard JSON quoting; output no spaces, indentation or trailing newline. Integers are decimal, booleans `true`/`false`. Unknown/undefined/float values are rejected.

Sort evolutions by numeric ID. For each evolution, sort each path's requirements by their canonical JSON string, then sort paths by their canonical JSON string. Arrays here are semantic sets/multisets, not authoring order; duplicate target paths are rejected. Priority is an explicit value so it is independent of list order. Preserve duplicate requirement multiplicity. Consequently reordering fields, entries, paths or requirements does not change hashes. The uploaded object is this readable, compact canonical JSON, not a binary blob.

Content hash = SHA256(UTF8(canonical complete normalized tree)). Version and development marker are included.

Leaf bytes = UTF8(canonical `{schema:1,familyId:<id>,evolution:<normalized entry>}`). Family/schema context prevents cross-family reuse. Version is omitted from the leaf so unchanged rules retain their identity across versions. Leaf hash = SHA256(0x00 || leaf bytes). Sort leaves by evolution ID. For each adjacent pair, sort the two 32-byte hashes lexicographically by unsigned byte, then parent = SHA256(0x01 || lower || higher). Duplicate the last node at each odd-sized level. A singleton root is its leaf hash. Empty trees are invalid. Repeat until one root remains.

Proof = `{evolutionId, siblings:[64-character lowercase hex SHA256 hashes, bottom to top]}`. No direction bits: pair sorting determines order. Verify the domain-separated leaf and each parent until matching the on-chain 32-byte root. Reject malformed hashes and proofs deeper than 16. Rust `verify_evolution_proof` takes canonical leaf bytes and binary siblings; a future gameplay instruction must build those bytes from strictly validated typed data and bind the expected family/schema rather than trusting arbitrary caller bytes.

Canonical fixtures are generated by `app/scripts/sample.ts`; Rust verifies the exact TypeScript-generated leaf, siblings and root. SHA-256 is standard in both implementations.
